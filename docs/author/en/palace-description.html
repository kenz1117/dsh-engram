·Terms and abbreviations

Words that occur frequently in the text but may mean something else for the author. This section need not be read in full — it is revisited when a term is not clear.

The memory palace (palace)
The plugin's memory store: memories (nodes), observations, entities, the profile. It lives in SQLite files in the plugin's data directory. “The palace” in our texts is this store, not the interface.
The panel (EngramPanel)
The plugin's interface inside DSH: the “Today”, “Library”, “Corridor”, “Log”, “Maintenance” tabs. The panel is the client half: it draws and does not decide what is written to the base.
The host (DSH), the fiber, the plugin
DSH is the application inside which the plugin lives. The fiber is the loaded instance of the plugin in the host process. “Restarting the plugin” means restarting DSH: the palace language is applied on the next start.
The palace language
The config.language key. It determines: which model the vectors are computed with, in which language the plugin writes service texts and instructions to the agent, in which language new memories will be written, and with which label the bases are signed. It changes semi-automatically: from a dialogue with the human or by answering in the window.
The interface language
The language of the panel's labels and service messages. It can be switched freely at any moment and affects neither the model, nor the palace language, nor the data. The two axes must not be confused — that is the main point of chapter 2.
The base label (model_label)
A string in the meta table of a base file, of the form ru-minilm-l12: language code, hyphen, short model name. The only thing we write into someone else's base. The language is the part of the label up to the first hyphen; the model name is not a language.
The registries (registry/*.json)
Shipped data instead of constants in the code: models.json — the model catalog (dimension, pooling, type), bindings.json — the “language → model” binding, languages.json — which languages the palace knows, schema.json — which tables carry vectors. The user layers lie in the data directory and take precedence over the shipped defaults.
The schema declaration
registry/schema.json. For each table: role (user or service), properties.vector.text — which field to read the text from, properties.vector.where — which rows participate. The vector field is not declared: it is derived as the only field of type BLOB.
The seven base states
absent — the file does not exist yet; empty — there are no memories; no-label — there is no label; other-model — the label is someone else's; mixed-dims — vectors of different lengths; missing-vectors — some memories have no vector; normal — everything is in place.
The four actions
none — nothing; write-label — write the label, leave the vectors alone; convert — recompute the vectors with the selected model; repair — fill in vectors for the memories that have none.
Vector recompute (conversion)
One operation for two occasions: moving to another model and repair. The criterion is one — a row of the schema scope whose vector is empty or whose length does not equal the expected one. The text of the memories does not change.
The embedder, the vector, the dimension
The embedder is the model that turns text into a vector (a set of numbers). The dimension is how many numbers the vector holds: bge-small-zh has 512, the multilingual minilm-l12 has 384. Vectors of different dimensions cannot be compared, so the dimension is a hard requirement, not a warning.
Cosine (similarity threshold)
A measure of closeness between two vectors, from 0 to 1. It decides whether memories count as duplicates (MERGE_COSINE = 0.92), whether merging is deferred (DEFER_COSINE = 0.88), whether they contradict each other (CONTRADICTION_COSINE = 0.88), and whether a memory is included in search (MIN_COSINE = 0.2).
Dictionary, built-in set, user layer
The dictionary is a file of “English string → translation”. The built-in set is the translations in code (src/i18n/catalog, src/client/locales). The user layer is a file in the data directory; it takes precedence over the shipped default and is not lost on reinstallation.
Curated profile
A block of rules that the person maintains themselves through the engram_profile_edit tool. It is inserted at the start of the session before the automatically derived profile and takes precedence over it. In the session text it arrives as a separate package, <engram_profile>.
Interlock guard
A checkbox that blocks a dangerous action by default. Clearing it is a separate, deliberate act by the person, not a setting.
Assembled condition
Our name for the rule that triggers the switch of the palace language: the language change, the cleared interlock guard and the pressed button are combined with “AND” inside a time window. If it did not come together, nothing happens.
Maintenance card
A panel section showing the state of the bases, the selected model, languages and dictionaries. It shows one summary word about the bases (“healthy”, “needs repair”, “needs conversion”) and a single button that performs what follows from the state.
Base snapshot
A copy of the base made with the VACUUM INTO command. Unlike copying the file, it is consistent: it does not catch the base mid-write.
Gate (check)
A mandatory check before shipping: types, text consistency, tests, code rules. “The gate is green” means “the check has passed”.
PR, upstream, branch
The upstream is the author’s repository (kenz1117/dsh-engram), our base is its tag v0.9.3. Our work lives in the work/dsv branch; two pull requests are already merged: #20 (Jev) on 21 October, #21 (the embedder and multilingual support) on 22 October.
Jev (System One)
An external check of memories at the author’s end. Our part is the interface and the substitution of values, not the provider check.
FTS (full-text search)
SQLite service tables for word search (nodes_fts and its shadows). They carry no vectors and do not go into base processing — in the schema declaration they are marked as role: service.
Locale
The operating system language. It is taken as is (“fr”, “ru”), without reducing it to our three languages: otherwise a French user would be offered English as if it were their own language.
Balloon (toast)
A pop-up message of the panel. The panel has its own mechanism and its own kinds: info, success, error, warning and reset — pastel pink for an event that happened by itself and broke nothing.

1.The task: why the palace did not work in other languages

The author’s memory palace is designed for two languages: Chinese and English. The interface texts and service messages sit in the code, the embedding model is Chinese (bge-small-zh, 512 numbers per vector), and the notion of “language” in the configuration was essentially one word: the string auto | zh | en | ru, hardcoded in TypeScript in four places. Three troubles followed from this, each of them visible on live data.

Trouble one: the language cannot be changed without breaking the bases

The model determines the vector length. Changing the model means getting bases where some vectors are of one length and some of another. Search over such data either breaks or quietly loses half the memories. At the same time, the base did not record what it was counted with: the only sign was the vector length, and that says nothing about the language.

Trouble two: a language cannot be added without rebuilding the plugin

The triple zh | en | ru lived in the code: in config validation, in parsing the base label, in the panel’s selection list and in the language set of the server half. A fourth language required editing TypeScript in each of the four places and a new release. For a tool that people install themselves this is unacceptable: language is data, not code.

Trouble three: two different things were called by the same word, “language”

The language of the panel labels switches freely, at any moment, and must not change anything in memory. The palace language holds the model, the instructions to the agent and the language of new memories. While both were called “language”, any decision about them was made at random. We split them into two axes — this is the first thing to understand about all the rest of the work.

How we framed the task Make the palace language an explicit state (visible and controllable), rather than a consequence of whichever model happens to be installed; make a new language addable as data — a dictionary file and a row in the bindings registry; and make any switch to another language always accompanied by a vector recompute, rather than leaving the palace in a state where “half is in one and half in the other”.

What already works

  • The palace language is determined on the first run and written to the configuration; the window with four choices works.
  • The base label <lang>-<model> is set in meta and read back; it shows whose base it is. Since 22.10 the label is set automatically when the base is opened — but only where that spoils nothing (chapter 4).
  • The registries models.json, bindings.json, languages.json, schema.json are data; a language and a model are added with a file.
  • The vector recompute from the maintenance card works and has been verified on live bases. Repair works separately: computing the missing vectors for records that have none, without changing either the language or the model (chapter 11).
  • Russian lives in the file i18n/ru.txt (485 texts, 501 lines in the file); English and Chinese remain in the author's code.
  • The dictionary is reconciled against the program with four numbers — keys in the program, lines in the file, without a translation, without a key (chapter 5).

What is not finished yet is in chapter 11, which also says what of it is our work and what awaits the author.

2.The palace axis: how the language is determined on first run

The palace language is not a setting for show. It holds too much to be set silently, so it is decided once and by a clear rule: if the person has already spoken with the agent in some language, that is the palace language; if there was no speech to go on — we ask.

What exactly counts as the person's voice

Utterances are taken only from the current session and only those where source.kind === 'user'. This matters more than it seems: the same events carry English service texts — a runtime snapshot, the skill catalog, agent instructions, insertions from other plugins. In a live check the palace erred on exactly these once: the “dialogue language” came out English because service text was taken for speech. After the fix, anything unfamiliar is not counted at all: erring towards “ask” is safer than assigning someone else's language.

Session logs are not read at startup. This is not caution but a cure: a log is read in full, and on live data that cost hundreds of megabytes of memory on every host start — once the host even crashed because of it. The utterances of the current session already sit in the process memory.

Threshold: when a language is considered determined

At least 40 letters in the sample are required, and the share of the dominant language must be at least 0.6. “privet” and “ok” do not determine the language — otherwise the palace would switch on one random phrase. The split follows the script: Cyrillic means Russian, ideographs Chinese, Latin English. A mixed utterance like “ok, spasibo” gives no voice at all.

Three cases the panel sees

CaseWhenWhat the palace does
autoThe person's speech is recognised, the bases are in the same language or do not exist yetWrites the dialogue language itself; the panel reports what it settled on
askThere were no utterances, or too few of themAsks in the window; the default is the Windows locale
mismatchDialogues are in one language and the base labels in another (or the bases are labelled in different languages)Shows the mismatch and leads into the same picker window

Why the locale is taken as is

The machine locale does not reduce to our three languages. A French user is offered “other language”, not English posing as his own — because substituting someone else's language is not help but a deception that surfaces a week later. If the locale could not be read, “other language” is not submitted: the person is told the code was not determined and is offered one of the palace's languages.

Writing the language is a separate tick after startup Editing the configuration on a starting fiber would take the normal path (a remount in the middle of applying settings), so the write is deferred to the next tick and goes the “live” path: the value changes on the fly, the plugin is not reloaded. Only a decision backed by the dialogue is written; the locale and the interface preference are too weak for that.

3.Changing the palace language: one assembled condition

Changing the palace language is not “one more setting alongside”. It changes what the palace will write with from now on, and therefore it goes together with the recompute of the bases — as one action, not two neighbouring ones. And it can only be started deliberately: three conditions are combined with an “AND”.

Why three conditions and not one button

The customer's wording was direct: “the user can start the conversion only deliberately: select another language, clear the checkbox, press the button — all in AND mode, and all actions within a minute. The minute has passed — everything reverted to what it was”. This guards not against a mistake in the code but against an accidental movement of the hand: the palace language cannot be changed “just to look” and then forgotten.

The window is thirty seconds, and it is a setting

The window length lives in the plugin settings (palaceChangeWindowSec), not as a constant in the code: it must be changeable without a rebuild. The countdown starts from the first of the three events — the language change or the removal of the interlock guard, whichever happened earlier. The window lives in the form itself, not on the server: it is a human's consent, not a background task. Two tabs get one form each, and a condition assembled in one cannot be completed by actions in the other — and that is how it should be.

Before “Run” is pressed, nothing is written to the configuration That is why “the window has passed” means “the form forgot the not-yet-assembled choice”, not “what was recorded has been rolled back”. There is nothing to roll back. The choice returns to the language the bases are on (it is taken from the label), and the interlock guard goes back on its own.

One request, not three

One request goes to the server with all three conditions, and the same request checks them. Otherwise calls spread over time could add up to a permission after the fact: “changed the language yesterday, cleared the tick today, pressed the button tomorrow” — and the result would be an action the human never assembled.

How it is done

The condition check is one pure function (src/registry/palace-change.ts), and both halves count by it: the panel decides what to show, the server decides whether to accept the request. Three things are checked: the language — an existing code and not the same one; the start of the window — real time, not from the future; the window has not expired. A rejection names the reason in words (“window expired”, “the same language is selected”), not with an error code.

“Run” sends one POST palace-change request, and that same request carries the matter through to the end: writes the language into the configuration, rewrites the base labels into the new language, recomputes the vectors. Separate “language first, bases after” steps do not exist, deliberately — the intermediate state “new language, old bases” would be seen by a human and not understood.

The button is still there for work without a language change: when the selected language matches the current one, no window is required, and the button stamps the label or computes the missing vectors. Otherwise repairing a base with memories without a vector would only be possible by “change the language and put it back”.

What can already be checked

The mechanics of the interlock guard and the countdown are checked by the “Panel test” button in the maintenance card: the same window opens in test mode, does not touch the configuration, and when the window expires shows a pink balloon “the interlock guard is back in place, the choice is reset”. Pink, not red: nothing broke, the event happened by itself.

What of this stands in the panel today The palace language switcher appeared on 22.10 and is described in the section “What was closed 22–23.10” (chapter 12): in the maintenance card it is the block “Palace language” — selection, interlock guard and “Run” in one row. The same button also works without a language change: when the selected language matches the current one, no window is required, and it stamps the label or computes the missing vectors. What is still missing is a separate indicator of divergence between the interface language and the palace language: a person who switched the interface “to look” does not see that the palace stands on another language.

4.Base label and language registry: language as data

So that the palace knows which language the base is on, one row is written into it — a label in the meta table:

key = model_label
value = ru-minilm-l12

The label is the only thing we write into someone else's base. Not dimensions, not time, not version: the dimension follows from the model catalog by the model name, while a copy would give a second source of truth that would sooner or later diverge from the first.

Who sets the label, and when

The label is not asked of the human at every convenient occasion, but it is not set “just in case” either. The rule is one — labelToStamp in src/registry/base-state.ts — and it works when the base is opened, before any button:

  • The base is empty — the label is set at once: we will write into it with that very model, there is nothing to argue about.
  • The base has no label, but the data is already on the target model — the label is applied: this is a signature, not a conversion, the vectors are untouched.
  • The base has no label, and the data is on a foreign model or of mixed dimensions — there is no label: that one needs a recompute, and a signature would lie. Such a base stays visible as “no label” until a human acts.
  • The label is already set — it is left alone: even if it names a foreign model, it is a fact about the data, not a reason to rewrite it.
  • The base could not be read (corrupt file, locked by a writer) — there is no signature: a base that looks empty may turn out to be foreign, merely unreadable at that moment. A read or write error does not prevent opening — the base simply remains without a label, and this is stated in the log.

The rule is the same as for the button: there is no second source of truth about the label. The only difference is that the button walks all bases at once and can recompute, while the signing on open cannot.

How the language is read from the label

The language is the part of the label up to the first hyphen. We split on the first one precisely because hyphens occur both in the model name (minilm-l12) and in the language subtag: zh-Hans-minilm-l12 yields zh, not “no label”. The model name is never counted as a language — this rule had to be introduced separately, because the temptation to “guess the language from the model” is great and always wrong.

The language code is no longer a closed list

Previously the allowed values lived as a string in the code. Now they are a file, registry/languages.json. The file has a user layer (<dbDir>/registry/languages.json): a new language is declared by a line next to the data, without editing the package — the line replaces the same-named one from the shipped default and does not require repeating the whole list. By the same path a language reaches both switchers: the server serves the panel dictionary on a separate route, the client declares the language to the host and registers the texts.

{ "formatVersion": 1,
  "languages": [
    { "code": "zh", "label": "中文",    "builtin": true  },
    { "code": "en", "label": "English", "builtin": true  },
    { "code": "ru", "label": "Русский", "builtin": false }
  ] }
  • label — what the language is called for a human in the selection list (the panel used to show ZH, now 中文).
  • builtin — whether the plugin has a built-in set of texts. Two are built in: zh (the author's) and en (the completeness reference). The rest come as a file.

The builtin flag is not there for looks: without it one cannot distinguish “the language exists but there are no translations yet” from “there is no such language at all”. The panel gets the language list from the server in the same response as the base state: its own copy of the triple has been removed from the client build, otherwise a language added by a file would appear on the server but not in the selection list.

The fourth choice passes the real code “Other language” is no longer turned into English. The locale code is written to the palace as is — for example fr. A palace with such a language works: it takes service texts in English (there is no built-in set for fr), understands memories, and once the file <dbDir>/i18n/fr.txt appears it will speak French. Substituting en instead would mean passing off a foreign language as “yours”.

What this gives the author

A new language is added with three pieces of data: a line in languages.json, a dictionary file, and a line in bindings.json (which model to count as this language). Not a single TypeScript edit, not a single rebuild. That is exactly why the language list is a file and not a constant: otherwise “support one more language” would mean “release a new version of the plugin”.

5.Dictionaries: what stays in code, what comes as a file

Interface and service-message translations live in two places, and this is not duplication but two different purposes. In code — what must always be there, with no files: two sets, English (the completeness reference and the source of keys) and Chinese (the author's wording). As a file — everything else, including Russian.

The dictionary key is an English string

The dictionary is keyed not by key names but by the English text: the English string on the left, the translation on the right, the separator a tab. This allows translations to be edited without knowledge of the code and does not break when a key is renamed. The price is that the English wording becomes part of the contract: if the text in the code changes, the translation will no longer be found. That is why texts are edited rarely, and this is a deliberate choice in favour of “editable without a rebuild”.

Two sets, two files

SetShipped default fileUser layer
Server messages (texts of tools, prompts, warnings)i18n/<lang>.txt<dbDir>/i18n/<language>.txt
Panel textsi18n/panel.<language>.txt<dbDir>/i18n/panel.<language>.txt

The sets are not mixed: identical English strings mean different things in them, so “Model and dictionaries” in the panel and in the messages are two different translations. Both sets share the same format, layers and parsing rules.

Fallback order

File dictionary → built-in set → English text. A missing file is neither an error nor an empty label: the English string stays. That is exactly why a new language can be declared before its translation is ready: the palace keeps working while the texts are translated gradually.

Editing translations from the panel

The maintenance card has a dictionary screen: a table of “English string — translation”, saving into the user layer (the shipped default belongs to the release, we do not edit it) and a “Translate” button. It sends the working model exactly those cells where there is no translation and does not rewrite what is already done; the translations that come back land in the panel draft, and the file is changed by “Save”. An empty cell removes the edit rather than writing an empty string; only what changed is saved, so that editing one cell does not wipe the others.

Dictionary reconciliation with the program

The dictionary screen answers not only “what is written here” but also “does it match the program”. Above the table stand four numbers that are computed on every opening, not by a button:

NumberWhat it means
keys in the programHow many strings the code itself declares — the reference we check against
strings in the dictionaryHow many strings are in the person's file, including placeholders without a translation
without translationThe program's keys have nothing to show: there is no text either in the edit or in the shipped default — they will go out in English
without keyFile strings whose left-hand side is not in the program: the key was renamed or deleted but the translation remained

The numbers are computed independently, and a match of the first two proves nothing: the keys could have diverged one for one. That is why the findings stand next to them, and each is clickable — “without translation” and “without key” filter the table. A string without a key cannot simply be thrown away: it is not lost on saving, otherwise the very first edit would erase a translation that the program still has nothing to attach it to.

The second thing that came out of this: the “Create” button no longer writes an empty placeholder. It lays out a file with all the program's keys and empty right-hand parts — the placeholder is visible in full at once, and “without translation” on it honestly equals the number of keys. The file still remains valid: an empty right-hand part is a placeholder, not breakage.

What goes to the model so that the terminology does not drift apart

The request is not a list of strings but an object with two keys: strings (what to translate) and glossary (the pairs already accepted in this same dictionary). The glossary is assembled from the translated strings of the set — short labels first — and grows as the pass goes on, so that one concept does not get different words in neighbouring batches. The instruction states outright: a word from glossary is not rewritten, one exact term per concept for the whole answer, no ambiguous words, no literal calques and no synonyms for the accepted one; and these are labels, not sentences.

Why the batch is exactly this size

In the working model, reasoning goes into the same output tokens as the answer. A measurement on the live model (French, panel set) showed where completeness ends:

BatchOutput tokensTimeTranslatedSame words on repeat
106963.8 s10 of 1010 of 10
202 61920.5 s20 of 2019 of 20
303 24413.3 s30 of 3027 of 30
404 41528.0 s40 of 4032 of 40
605 80730.7 s59 of 6050 of 59

With the former output limit of 4096 tokens, a batch of forty terms broke off in the middle, and only part of the pairs was salvaged from the answer — hence the complaint “filled in half”. Hence the settings: a batch of 30 strings, an output limit of 16 384 tokens (headroom for the wandering length of the reasoning), a batch length limit of 2400 characters and a wait of 180 seconds.

French: the whole path end to end, without base conversion

Verified on the live data catalog: the language fr was declared in the registry, empty i18n/fr.txt and i18n/panel.fr.txt were created, filled by the working model through the same code as the button, and declared to the host at startup — the language landed in both pickers, the palace's and the interface's. No vector recompute was started: a language can be introduced without touching the bases.

The result of that run: 468 strings out of 481 in the messages dictionary and 478 out of 493 in the panel dictionary. The remainder was analysed rather than written off as “the model could not”. Thirteen strings of the messages set are placeholders made of substitutions alone (“{reason} {count}”, “, ”, “—”): there is nothing to translate in them, and now they do not go into the request at all. The other twelve are words that are written the same in French as in English (Provenance, messages, base, Pause, Concepts, contradiction, Adjacent, consolidation, Jev): the translation would coincide with the source, and by the rule a coincidence means “no translation” — and that is correct, a French speaker sees exactly the same word.

State as of 23.10 (live data catalog): fr.txt holds 460 pairs and not a single empty right-hand part, panel.fr.txt — 480. The key set has grown to 488 since then, so the French dictionary again has strings “without translation” — that is a normal state, not breakage: new keys arrive in English until they are translated with the same button. It is precisely for such cases that the dictionary reconciliation with the program appeared (see above).

The terminology did not come out as a calque: Room → Salle, Corridor → Couloir, Placard → Cartel (a museum label, not “placard” — a cupboard), Memory Palace → Palais de mémoire, Tour → Visite.

Two fixes came out of a run. First: a batch from which not a single pair was accepted (the model spent the whole allowance on reasoning) is split in half and asked again — otherwise filling stopped with the error “the model reached its limit” — and the person saw an unfinished dictionary. Second: the instruction now explains what the tool itself means (the palace is a memory store, a room is a category, a corridor is links, a placard is a record title, repetition is intervals), because the model refused to translate short labels like Pause or Capture as ambiguous.

Why Russian is not in the code Russian was our first experience of a “language as data”, and it went through end to end: 485 texts in a file, edits without a rebuild, shipped and user layers, a consistency check against the key set. The second experience was French: an empty dictionary, translation by the model, the language in both pickers, and not a single code change for a language. This is no longer a hypothesis but a proven path.

6.Model, bindings and vector dimension

The model is not chosen “in the settings” but by the language of the palace. There is one rule: a binding language → model in bindings.json, otherwise the default *. A separate setting can override the choice, but that is a deliberate exception, not the usual path.

// registry/models.json — что модель умеет
{ "id": "Xenova/paraphrase-multilingual-MiniLM-L12-v2",
  "label": "minilm-l12",          // короткое имя: попадает в метку базы
  "pooling": "mean", "dtype": "q8", "dimensions": 384 }

// registry/bindings.json — какой моделью считать язык
{ "bindings": { "zh": "Xenova/bge-small-zh-v1.5", "*": "Xenova/paraphrase-multilingual-MiniLM-L12-v2" },
  "default": "en" }

What matters here

  • Dimension comes from the catalog, not from the code. bge-small-zh has 512 numbers, the multilingual minilm-l12 has 384. The recompute takes the expected length from there; there is no longer a constant in the converter.
  • The language of the model is not an indicator. A Chinese model does not at all mean “a base in Chinese”: the language comes from the label, and the model from the binding. The same multilingual model can serve Russian, English and French, and the labels of the bases will differ.
  • Dimension is a hard condition on writing, a soft one on reading. A vector of foreign length cannot be written: it will not compare with the others. A base with a foreign length can be read — search degrades to word search, but it does not fall silent and does not lose records.
  • The package default (default) is accepted only if the release actually ships texts for it. A declared but empty language is worse than English.
  • A remote model is a separate choice. If an OpenAI-compatible endpoint is selected in the settings, the local entry is not chosen at all, and the dimension is learned from the first vector: for such a model there is nowhere to declare it. The base label is still assembled the same way — from the language and the name — otherwise there would be nothing to check the base against.

Thresholds visible in behavior

ThresholdValueWhat it decides
MIN_COSINE0,2Below it a record does not enter semantic search
MERGE_COSINE0,92Above it records are considered the same
DEFER_COSINE0,88Above it merging is deferred until a re-check

7.Base schema: how the handler knows what lies where

The list of tables with vectors must not live in the code. Otherwise a table added by the author silently drops out of all our operations: recompute, repair, state check. So it is declared as data — the file registry/schema.json — and is read by the same rules as the model catalog: the shipped default is mandatory, and the user layer in the data directory overrides it.

What is declared and what is inferred

  • Declared: the table role (user or service), the field holding text for the model (properties.vector.text) and the condition for row participation (properties.vector.where).
  • Inferred: the vector field is the only field of type BLOB in a table row. If there are two BLOB fields, the declaration is rejected with a complaint: it is unclear where to write.
  • Not declared at all: the dimension. It follows from the model catalog by label, not from the schema file.
{ "formatVersion": 1, "schemaVersion": 13,
  "tables": {
    "nodes":        { "role": "user",
                      "properties": { "vector": { "text": "content", "where": "status = 'active'" } },
                      "fields": { "id": "TEXT", "content": "TEXT", "embedding": "BLOB", "...": "..." } },
    "observations": { "role": "user",
                      "properties": { "vector": { "text": "belief", "where": null } } },
    "nodes_fts":    { "role": "service" }
  } }

The service tables are listed as a clear example of the walker skipping what is marked without analysing its contents: FTS shadows carry no user vectors, and an attempt to process them would be a mistake. For observations the condition null means “all rows participate”: observations are not archived the way memories are.

Seven states and four actions

StateWhat is visibleAction
absentThere is no base file yet (it is created by the author's code)none
emptyThe file exists, there are no records in the schema scopenone
no-labelThere is no label; the model is guessed from the vector lengthwrite-label or convert
other-modelA label exists, but the model is not the one we will write withconvert
mixed-dimsThe vector length does not match the labelconvert
missing-vectorsSome of the records have no vectorrepair
normalThe label matches, all vectors are of that lengthnone

The order of the checks matters and is fixed: a mismatch must not be declared before it is established whose base this is — otherwise a foreign model would look like corrupted vectors. The rule is pure: it receives facts about the base and an expectation, and returns a state and an action. That is why it is verified by a test with no disk and no SQLite, and the panel merely names it in words.

How the recompute proceeds

  1. Plan. A separate connection in “read-only” mode walks the tables from the declaration and selects the rows of the scope whose vector is empty or whose length is not the expected one.
  2. Batches. Texts go to the model in batches of 16: the model's output limit must not decide the fate of the whole base.
  3. Writing. The vectors are written by the storage — the base has a single connection, and it lives there. The converter only reads and computes.
  4. Label. After a successful recompute the base label is rewritten to the new language and model. The label and the vectors change in one operation, not two.

Empty text is not a failure but a fact about the content: the row has nothing to build a vector from. Such rows are reported as a separate number, not silently skipped and not lumped into the overall error count.

Repair: compute the missing vectors and sign the base without changing the language

The missing-vectors state means records whose vector is empty while the label may well be correct. Running a recompute of the whole base for the sake of six rows is unnecessary and harmful: the other vectors are already correct. That is why this state has its own action — repair — and the button executes it as two requests in a row: base-label writes the missing labels, base-convert computes what lacks a vector.

The practical point: a base with records lacking a vector stops being called “needs repair” after a single click, and for that one does not have to change either the language of the palace or the model. The price of such a repair is exactly one recompute of what is missing, not of the whole file.

Boundaries: what we deliberately do not build

  • There is no restore machinery. Conversion is a one-off human action; a rollback to the previous state is not provided for. Only a checkpoint is needed, so that an interrupted recompute can be continued: a partially recomputed base is the mixed-dims state, and a repeated run carries the work through to the end.
  • The recompute goes straight into the live base, with no temporary copy: the base is small, and a copy would double both space and time. The fallback path is the base export, which the author already has.
  • What cannot be converted is reported separately. A row that failed to be recomputed is not lost and does not block the others: it lands in the report as a separate list with the reason.
What the recompute does not do It does not change the text of records, does not create or drop tables, does not touch service tables. The plan is a read: if it never comes to pressing “Run”, the same rows, texts, vectors and label remain in the base. This is verified by a test, not promised.

8.Curated profile: why the rules moved into a separate packet

The palace holds two kinds of knowledge about a person: the inferred profile (what the system inferred on its own) and the curated block — the rules a person wrote themselves via engram_profile_edit. The second outranks the first, and that is where the trap lay.

What was wrong

The curated block was inserted at the start of the session mixed together with the inferred profile and with historical memories, in the common memory text. The agent read side by side “rules maintained by the person” and “memories that may be wrong”, and there was nothing to tell them apart except their wording. The second half of the problem was the memory block itself: it receives records the person did not write, and they looked just like rules.

What was done

The rules now arrive as a separate packet <engram_profile> with its own header-guidance: these are the person's instructions, they must be followed and treated as primary — as opposed to the memories below, which are only material. The separate tag exists so that the protection against substitution can distinguish a marked-up packet from text that merely looks like markup.

Two attempts, and the first was cancelled At first we wanted a “cheap fix”: to prepend a header inside the existing memory block. We cancelled it and did the expensive but correct thing: a header inside shared text does not separate rules from memories, it only adds one more formulation that can be confused with the content. A separate package is a separate place, a separate tag, a separate check.

What this gives

  • The person’s rules are visible separately from the system’s conclusions — to the person, to the agent, and to the security check.
  • The block is not “diluted”: anything not written by the person does not get into it.
  • Editing, rollback and version history live in one place, with optimistic locking: an edit does not silently overwrite someone else’s edit.

9.What we fixed along the way and why

The work did not happen beside the author’s code but through it: while we were doing multilingual support, defects that got in the way surfaced. Below is what was fixed in passing. This is not “rewrote it while we were there”: every item once got in the way, and without it the next step could not be taken.

Interface

  • The panel menu no longer slides away. The menu and the tabs were part of the scrollable content, so the page “slid” underneath them, and with a long list the menu disappeared from view. Now the menu is pinned to the top and does not take part in content scrolling. For the same reason the layers were reworked: the full-screen dictionary edit screen opened “at the click position” and on a long card ended up past the bottom edge — from the outside it looked like “clicked and nothing happened”. Now the layers live outside the scrollable area.
  • The buttons on the dictionary screen came to life. Save, cancel and model fill were markup without handlers: the screen opened and then nothing happened. Now only what changed is saved, an empty cell removes the edit, and model fill writes a draft, not a file.
  • The panel language follows the host. Previously the panel kept its own choice and could speak one language while the host was switched to another. Now the source is the DSH setting, and a manual panel language choice remains a deliberate override.
  • The maintenance card texts come from the panel’s built-in dictionaries. The card read a server-side language file, so its labels did not switch together with the interface and could end up in a language the person does not expect.
  • The full model identifier was removed from the selection row (Xenova/paraphrase-multilingual-MiniLM-L12-v2 instead of the short name took the whole row and pushed out the rest). The identifier remains in the hover tooltip.
  • The panel check window: the button is pushed to the right, closing is reported to the panel (otherwise the window opened only once — the panel considered it still open), the text is larger and higher-contrast: grey 11–12 px was not readable in that window.

Memory and host

  • Session logs are not read at startup. Reading the log in full cost hundreds of megabytes of memory on every startup; on live data the host crashed because of it. Turns are taken from the current session, and the log is read only on an explicit history backfill request. The logs on disk are not deleted by this: they remain, and deletion is a separate action with confirmation.
  • Only what the person typed counts as the dialogue language. A live check showed that the “dialogue language” was determined to be English, because English service text (runtime snapshot, skill catalog, instructions) was taken for human speech. Now anything that lacks the mark of a human turn is not counted at all.
  • The embedder shuts down correctly, otherwise resources kept hanging after a model reload.

Data and vectors

  • Dimension is a hard condition on write, degradation on read. Previously a dimension mismatch was a warning: the base quietly filled up with vectors that would never be compared with anything. Now the write is rejected deliberately, and reading keeps working via keyword search — and says so with the degraded flag instead of staying silent.
  • The base dimension is taken from the majority of vectors, not from the first one encountered: a mismatch no longer passes itself off as the “norm”.
  • The schema declaration format version is no longer a dead field: formatVersion is checked, and a declaration of another version is not applied silently.
  • The migration record is shown in words, not as a chunk of JSON: a person reads the output, not the structure.
  • A button to clear the palace log with confirmation and a clear result.
Why this list is in the document Because half of these fixes change behaviour that the author considers their own. They must not be “noted”, but either accepted upstream or deliberately rejected. Each fix was made as a separate commit with an explanation in the body, so that it can be reviewed one by one.

Before a recompute the bases are snapshotted with VACUUM INTO, and the snapshot remains reproducible evidence: it shows what was there. 11.Maintenance: base states, repair, and the log

The maintenance card answers three questions in a row: what is up with the bases, what will happen to them when pressed, and why last time it came out exactly that way. The third question previously went unanswered — and it showed.

Three words instead of seven states

The rule sorts a base into one of seven states (chapter 7), but a person at the card does not need seven: they have one button. So the card reduces the states to three words, and the word is chosen by what the button will do:

Word in the cardWhenWhat “Run” does
Base is OKAll bases in state normal, absent or emptyNothing: there is nothing to press
Base needs repairOnly labels and vector backfill are neededA repair: base-label, then base-convert
Base needs conversionAt least one base needs a recompute onto another modelA language switch by the assembled condition, or a recompute by state

Inside the card each base still names its own state — no label, another model, mixed vectors, memories without a vector — otherwise it would be impossible to tell which of the six bases to repair. The summary word, though, is one for all bases: there is one button, and it has to name itself honestly.

The log: two entries that did not exist before

A failed Jev decision has so far lived only in a ring buffer in process memory. The buffer dies with a restart, and a day later “the record passed under clean rules” and “Jev was silent” became indistinguishable in the log. Now every failure writes a jev-fallback line: where it was asked (band or contradiction), which question, which reason and how long it took. The memory text does not get into the log: the log must not become a second store of other people's records, and a log error has no right to break a memory write — that is why it is silenced there.

The second line is vectors-missing. It appears when the distillation of records (distill) has passed but there was nothing to place a vector with: records without a vector remained in the base. It carries the number of records and the scope. This is exactly the case later seen as “the base requires repair”; before, the cause disappeared and a person saw only the consequence.

The panel shows both lines in plain language rather than by service names: the operations list holds “Jev decision failed” and “records without vector”, with an explanation in the tooltip.

Jev check line

The “Test connection” button showed its result in a toast, and a toast lives for seconds: a minute later one could say neither where the check went nor how it ended. Now above the form there is a line with the parameters — address, model, timeout and where the key came from (“from the field”, “stored”, “not set”) — and below it the outcome of the last check: time, response duration, ping probability and HTTP code.

The refusal got a name. Before, any failure looked the same — “not specified” — and a person did not know whether to fix the key, the network, the timeout or the protocol. Now the kind of failure is named: HTTP (the server answered, but with the wrong thing), network (could not reach), timeout (did not make it in time), protocol (an answer came, but there is nothing to parse it with). The full error text sits in the tooltip so the line does not fall apart.

The measurement is taken from a live connection: the line shows the duration and the probability that the response itself returned, not the last known success, and the HTTP code next to them. The numbers in it change from run to run — that is the sign that it is alive.
