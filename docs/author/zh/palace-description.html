·术语与缩写

这些词在文中经常出现，而在作者那里可能含义不同。不必把这一节通读一遍——遇到不理解的术语时再回来查。

记忆宫殿（palace）
插件的记忆存储：记忆（nodes）、观察项（observations）、实体、档案。它以 SQLite 文件的形式存放在插件的数据目录中。我们文中的「宫殿」指的就是它，而不是界面。
面板（EngramPanel）
DSH 内插件的界面：标签页「今天」「库」「走廊」「日志」「维护」。面板是客户端那一半，它负责绘制，不决定往库里写什么。
宿主（DSH）、Fiber、插件
DSH 是插件所运行于其中的应用。Fiber 是宿主进程中已加载的插件实例。「重启插件」指的是重启 DSH：宫殿语言在下次启动时生效。
宫殿语言
键 config.language。它决定：向量按哪个模型计算，插件用哪种语言写面向代理的服务文本与指令，新记忆使用哪种语言，库用哪个标记署名。它半自动变更：依据人的对话或窗口里的回答。
界面语言
面板文字与服务消息的语言。可随时自由切换，不影响模型、不影响宫殿语言，也不影响数据。两条轴不能混淆——这是第 2 章的主旨。
库标记（model_label）
库文件 meta 表中的一行，形如 ru-minilm-l12：语言代码、连字符、模型短名。这是我们写入他人库的唯一内容。语言是第一个连字符之前的那部分标记；模型名不是语言。
注册表（registry/*.json）
以数据代替代码中的常量：models.json — 模型目录（维度、池化、类型），bindings.json — 「语言 → 模型」绑定，languages.json — 宫殿认识哪些语言，schema.json — 哪些表带有向量。用户层位于数据目录中，优先级高于随包提供的内容。
模式声明
registry/schema.json。对每张表：role（user 或 service）、properties.vector.text — 从哪个字段读取文本、properties.vector.where — 哪些行参与。向量字段不声明：它作为唯一一个 BLOB 类型的字段推导出来。
库的七种状态
absent — 文件还不存在；empty — 没有记忆；no-label — 没有标记；other-model — 标记属于别的模型；mixed-dims — 向量长度不一致；missing-vectors — 部分记忆没有向量；normal — 一切就位。
四个动作
none — 什么都不做；write-label — 写入标记，不碰向量；convert — 按所选模型重算向量；repair — 为缺少向量的记忆补写向量。
向量重算（转换）
一种操作应对两种场合：迁移到另一个模型和修复。判据只有一个——模式作用域中向量为空、或长度不等于预期的那一行。记忆文本不变。
嵌入器、向量、维度
嵌入器是把文本转成向量（一组数字）的模型。维度是向量中包含多少个数字：bge-small-zh 是 512，多语言 minilm-l12 是 384。不同维度的向量无法比较，因此维度是硬性条件，而不是提示。
余弦（相似度阈值）
衡量两个向量接近程度的度量，取值 0 到 1。它决定是否把记忆当作重复项（MERGE_COSINE = 0.92）、是否推迟合并（DEFER_COSINE = 0.88）、是否互相矛盾（CONTRADICTION_COSINE = 0.88），以及某条记忆是否进入搜索（MIN_COSINE = 0.2）。
词典，内置集合，用户层
词典是「英文字符串 → 译文」的文件。内置集合是代码里的译文（src/i18n/catalog、src/client/locales）。用户层是数据目录里的文件，优先级高于随包提供的部分，重装时不会丢失。
人工维护的档案
由人自己通过 engram_profile_edit 工具维护的规则块。它在会话开头被插入，位置早于自动推导出的档案，且优先级高于后者。在会话文本中以单独的数据包 <engram_profile> 形式出现。
联锁保险
默认状态下阻止危险动作的复选框。取消勾选是人一次单独的、有意识的操作，而不是一项设置。
已凑齐的条件
我们对触发宫殿语言切换的那条规则的叫法：语言切换、已解除的联锁保险和按下按钮，在同一个时间窗口内按「与」组合。条件没凑齐，就什么也不会发生。
维护卡片
面板中显示各库状态、所选模型、语言和词典的区域。它给出一句关于各库的汇总判断（「正常」「需要修复」「需要转换」），以及一个按钮，用来执行当前状态所要求的动作。
库快照
由 VACUUM INTO 命令生成的库副本。与直接复制文件不同，它是一致的：不会在写入的瞬间抓到库。
门禁（检查）
随包提供前必须做的检查：类型、文案一致性、测试、代码规则。「门禁是绿的」意思是「检查已通过」。
PR、上游、分支
上游是作者的仓库（kenz1117/dsh-engram），我们的基线是它的标签 v0.9.3。我们的工作放在 work/dsv 分支上；两个 pull request 已经合并：#20（Jev）——10 月 21 日，#21（嵌入器与多语言）——10 月 22 日。
Jev (System One)
作者那边的记忆外部检查。我们这一部分只涉及界面和取值替换，不涉及对提供方的检查。
FTS（全文搜索）
SQLite 中用于按词搜索的辅助表（nodes_fts 及其影子表）。它们不承载向量，不参与库的处理——在模式声明中标为 role: service。
区域设置
操作系统的语言。原样取用（「fr」「ru」），不归并到我们的三种语言：否则法国人会被当成英语用户而拿到英语。
气泡提示（浮层提示）
面板的弹出消息。面板有自己的机制和种类：info、success、error、warning 和 reset——淡粉色，用于自行发生且未破坏任何东西的事件。

1.任务：宫殿为什么在其他语言下不工作

作者的记忆宫殿只支持两种语言：中文和英文。界面文案和辅助消息写在代码里，嵌入模型是中文的（bge-small-zh，每个向量 512 个数），而配置里的「语言」概念实际上只是一个词：字符串 auto | zh | en | ru，以 TypeScript 形式写死在四个地方。由此生出三个问题，每一个在真实数据上都能看到。

问题一：换语言就必然弄坏库

模型决定向量长度。换模型就意味着得到这样的库：一部分向量是一个长度，另一部分是另一个长度。在这种数据上搜索要么直接崩溃，要么安静地丢掉一半记忆。而且库里没有记录过它自己是按什么算出来的：唯一的标志是向量长度，而向量长度对语言什么也说明不了。

问题二：不重新构建插件就加不了语言

三元组 zh | en | ru 活在代码里：在配置校验里、在库标记的解析里、在面板的选择列表里，以及在服务端那一半的语言集合里。加第四种语言需要在四个地方各改一处 TypeScript，并重新发版。对于一个让人自己安装的工具，这不可接受：语言是数据，不是代码。

问题三：两件不同的事都叫「语言」

面板标签的语言可以随时自由切换，且不应改变记忆中的任何东西。宫殿语言则决定模型、给智能体的指令以及新记忆的语言。当两者都叫「语言」时，任何关于它们的决定都是凭感觉做的。我们把它们拆成两条轴——这是理解后面全部工作的第一件事。

我们如何界定这个问题 让宫殿语言成为显式状态（可见且可控），而不是恰好装着哪个模型的结果；让新语言只靠数据添加——一个词典文件加一行绑定注册表记录；并且让切换语言始终伴随向量重算，而不是把宫殿留在「一半用一种语言、一半用另一种语言」的状态。

其中已经可用的部分

  • 宫殿语言在首次启动时确定并写入配置；带四个选项的窗口可用。
  • 库标记 <语言>-<模型> 写入 meta 并可反向读出；由它可以看出库属于谁。自 22.10 起，标记在打开库时自动写入——但仅限不会破坏任何东西的场合（第 4 章）。
  • models.json、bindings.json、languages.json、schema.json 都是数据；语言和模型通过文件添加。
  • 从维护卡片发起的向量重算可用，并已在现用库上验证。另有独立的修复功能：为没有向量的记忆补算，不改动语言，也不改动模型（第 11 章）。
  • 俄语存放在 i18n/ru.txt 文件里（485 条文本，文件 501 行），英语和中文仍留在作者的代码中。
  • 词典与程序通过四个数字核对——程序中的键数、文件中的行数、未翻译数、无键数（第 5 章）。

尚未完成的部分在第 11 章，那里也说明了其中哪些是我们的工作、哪些要等作者处理。

2.宫殿的轴心：首次启动时如何确定语言

宫殿语言不是「看看就好」的设置。它承载的东西太多，不能默默设定，因此只决定一次，并且依据一条清晰的规则：如果人已经用某种语言与代理说过话，那就是宫殿语言；如果没有可依据的言语，就去问。

什么才算人的发言

发言只取自当前会话，且只取 source.kind === 'user' 的那些。这比看起来更重要：同一批事件里还会进来英文的服务性文本——运行时快照、技能目录、代理指令、其他插件的插入内容。在实机检查中，宫殿正是因此在这一点上错过一次：「对话语言」变成了英语，因为服务性文本被当成了言语。修正后，一切不熟悉的内容都不再计入：往「询问」的方向错，比指派一门外语更安全。

启动时不读取会话日志。这不是谨慎，而是补救：日志是整份读取的，在真实数据上，每次宿主启动都要花掉数百兆内存——宿主曾因此崩溃过一次。当前会话的发言本来就在进程内存里。

阈值：何时认定语言已确定

样本中至少需要 40 个字母，且主导语言的占比不低于 0,6。仅凭「你好」和「ok」不会判定语言——否则宫殿会因为一句偶然的话就切换。划分依据文字系统：西里尔字母为俄语，汉字为中文，拉丁字母为英语。像「ok, 谢谢」这样的混合发言完全不算作依据。

面板看到的三种情形

情形何时宫殿的做法
auto识别出人的言语，库为同一语言，或尚无库自行写入对话语言，面板提示依据为何
ask没有发言或发言太少在窗口中询问；预置值为 Windows 区域设置
mismatch对话为一种语言，库标记为另一种（或各库标记的语言不同）显示不一致，并引导至同一个选择窗口

为何区域设置原样采用

机器的区域设置并不限于我们这三种语言。给法国人提供的是「其他语言」，而不是冒充其母语的英语——因为拿外语顶替不是帮助，而是欺骗，一周后就会暴露。如果区域设置读取失败，不会提交「其他语言」：会告知用户代码未能确定，并请其从宫殿的语言中选择一种。

语言写入是启动后的单独一拍 在正在启动的 fiber 上修改配置会走常规路径（在应用设置过程中重新挂载），因此写入被推迟到下一拍，并走「实时」路径：值在运行中改变，插件不重新加载。只有依据对话作出的决定才会被写入；区域设置和界面 preference 对此来说太弱。

3.切换宫殿语言：一个合并后的条件

记忆宫殿的语言切换不是「旁边又多了一个设置」。它改变的是宫殿此后写入所用的语言，因此它与库的重算绑在一起——是一个动作，而不是两个相邻的动作。而且它只能被有意识地启动：三个条件按「与」叠加。

为什么是三个条件而不是一个按钮

委托方的表述很直接：「用户只能有意识地启动转换：选择另一种语言、取消复选框、按下按钮——全部按「与」组合，且所有动作都发生在一分钟内。一分钟过去——一切回到原来的状态。」这不是防代码出错，而是防手一挥：宫殿语言不能「随手看看」改掉然后忘掉。

窗口是三十秒，而且它是设置项

窗口长度存放在插件设置里（palaceChangeWindowSec），而不是代码中的常量：改它不需要重新构建。计时从三个事件中第一个开始——语言切换或解除联锁保险，哪个先发生算哪个。窗口存在于表单本身，不在服务器上：这是人的同意，不是后台任务。两个标签页各有自己的表单，不能用另一个标签页里的动作把条件在一处拼齐——本就该如此。

点击「执行」之前，不向配置写入任何内容 因此「窗口过去了」的意思是「表单忘掉了未拼齐的选择」，而不是「回退了已写入的内容」。没有可回退的东西。选择回到库当前所用的语言（取自标记），联锁保险自行复位。

一个请求，不是三个

发往服务器的是一个带有全部三个条件的请求，也由它来做校验。否则分散在不同时间的调用可能事后拼成一个许可：「昨天换了语言、今天取消勾选、明天按了按钮」——于是产生一个并非此人拼齐的动作。

实现方式

条件校验是一个纯函数（src/registry/palace-change.ts），两侧都按它计算：面板决定显示什么，服务器决定是否接受请求。校验三件事：语言——是已存在的语言代码且不是同一个；窗口起点——是当前时间，不来自未来；窗口未过期。拒绝时用文字说明原因（「窗口已过期」、「选择的仍是同一语言」），而不是错误码。

「执行」发送一个 POST palace-change 请求，也由它把事情做完：把语言写入配置、把库的标记改写为新语言、重算向量。刻意没有单独的「先语言、后库」——「语言是新的、库是旧的」这种中间状态会被人看到，且看不懂。

按钮也保留给不换语言的作业：当所选语言与当前语言一致时不需要窗口，按钮只打标记或补算向量。否则要修复带有无向量记忆的库，就只能「换语言再换回来」。

现在已经可以验证什么

联锁保险与计时的机制可用维护卡片里的「面板测试」按钮验证：同一个窗口在测试模式下打开，不碰配置，窗口过期时显示粉色气泡「联锁保险已复位，选择已重置」。是粉色而非红色：什么都没坏，事件是自己发生的。

这些今天在面板里已经有哪些 宫殿语言切换器于 22.10 出现，并在「22–23.10 已完成的内容」一节（第 12 章）中描述：在维护卡片里是「宫殿语言」区块——选择、联锁保险和「执行」在同一行。同一个按钮不换语言也能用：所选语言与当前语言一致时不需要窗口，它只打标记或补算向量。至今仍然没有的是——界面语言与宫殿语言不一致的单独指示：把界面切过去「看看」的人，看不到宫殿还停在另一种语言上。

4.库标记与语言注册表：语言即数据

为了让宫殿知道库停在哪种语言上，会往库里写一行——meta 表中的标记：

key = model_label
value = ru-minilm-l12

标记是我们写入别人库里的唯一内容。没有维度、没有时间、没有版本：维度可由模型目录按模型名推得，而副本会成为第二个真相来源，早晚与第一个不一致。

谁在什么时候打标记

标记不会一有机会就问人，但也不会「以防万一」就写上。规则只有一条——src/registry/base-state.ts 中的 labelToStamp，它在打开库时生效，早于任何按钮：

  • 库为空——立刻打上标记：之后就用那个模型写入，没有可争的。
  • 库没有标记，但数据已经在目标模型上 — 会打上标记：这只是一条标注，不是转换，向量不动。
  • 库没有标记，而数据在别的模型上或处于混杂状态 — 不打标记：那里需要重算，标注会撒谎。这样的库会一直显示为「没有标记」，直到人采取动作。
  • 标记已经存在 — 不动它：即使它说的是别的模型，那也是关于数据的事实，不是重写的理由。
  • 库读取失败（文件损坏、被写入者占用）— 不打标注：看起来空的库可能其实是别人的，只是此刻读不出来。读取或写入错误不妨碍打开 — 库只是没有标记，日志里会说明这一点。

规则和按钮那条一样：标记没有第二个真相来源。区别只在于，按钮一次遍历所有库并且会重算，而打开时的标注不会。

如何从标记读取语言

语言是标记在第一个连字符之前的部分。之所以按第一个切，是因为模型名里也有连字符（minilm-l12），语言子标签里也有：zh-Hans-minilm-l12 得到 zh，而不是「没有标记」。模型名永远不算语言 — 这条规则不得不单独加，因为「按模型猜语言」的诱惑很大，而且永远是错的。

语言代码不再是封闭列表

以前允许的取值是代码里的一行字符串。现在它们是文件 registry/languages.json。该文件有用户层（<dbDir>/registry/languages.json）：新语言在数据旁用一行声明，无需改动包 — 该行替换随包提供的同名行，而不需要重复整个列表。语言以同样的方式进入两个切换器：服务器通过单独的路由返回面板词典，客户端向宿主声明语言并注册文本。

{ "formatVersion": 1,
  "languages": [
    { "code": "zh", "label": "中文",    "builtin": true  },
    { "code": "en", "label": "English", "builtin": true  },
    { "code": "ru", "label": "Русский", "builtin": false }
  ] }
  • label — 语言在选择列表里对人怎么称呼（以前面板显示 ZH，现在是 中文）。
  • builtin — 插件有没有内置文本集。内置的有两套：zh（作者自己的）和 en（完整性样本）。其余的都来自文件。

builtin 这个标志不是为了好看：没有它就无法区分「语言存在但还没有译文」和「根本没有这门语言」。面板用与库状态同一个响应从服务器拿到语言列表：客户端构建里的那份三元组副本已删除，否则通过文件添加的语言会出现在服务器上，却不在选择列表里。

第四个选项传递真实代码 「其他语言」不再变成英语。给记忆宫殿写入的是原样的区域代码 — 例如 fr。带这种语言的记忆宫殿可以工作：服务性文本取英语（fr 没有内置集），记忆能理解，而一旦出现 <dbDir>/i18n/fr.txt — 它就会说法语。用 en 顶替则意味着把别人的语言当成「你的」。

这对作者意味着什么

新增一门语言只需三份数据：languages.json 里的一行、词典文件，以及 bindings.json 里的一行（用哪个模型来对应这门语言）。不用改一行 TypeScript，也不用重新构建。正因如此，语言列表是文件而不是常量：否则「再支持一门语言」就意味着「发布插件的新版本」。

5.词典：什么留在代码里，什么以文件形式提供

界面和服务消息的译文存在于两处，这不是重复，而是不同的用途。代码里是那些必须始终存在、不依赖文件的东西：两套集合，英语（完整性样本和键的来源）和中文（作者的措辞）。文件里是其余一切，包括俄语。

词典的键是英语字符串

词典不是按键名，而是按英语文本：左边英语字符串，右边译文，分隔符是制表符。这样可以在不了解代码的情况下修改译文，而且键改名后也不会失效。代价是英语措辞成了契约的一部分：如果改动代码里的文本，译文就找不到了。所以文本很少改动，这是为了「无需重建即可修改」而做的自觉取舍。

两套集合，两个文件

集合随包文件用户层
服务端消息（工具、提示词、警告的文本）i18n/<语言>.txt<dbDir>/i18n/<语言>.txt
面板文本i18n/panel.<语言>.txt<dbDir>/i18n/panel.<语言>.txt

两套条目不会混用：相同的英文字符串在两者中含义不同，因此「模型与词典」在面板里和在消息里是两个不同的译法。两者的格式、层级和解析规则是共通的。

回退顺序

文件词典 → 内置条目 → 英文原文。文件缺失不是错误，也不是空标签：会保留英文字符串。正因如此，新语言可以在翻译就绪之前先声明：记忆宫殿照常工作，文本则逐步翻译。

从面板编辑译文

维护卡片里有词典界面：一张「英文字符串 — 译文」表格，保存到用户层（随包提供的部分属于发行版，不予修改），以及 「翻译」按钮。它只把没有译文的单元格发给工作模型，不重写已有译文；返回的译文进入面板草稿，再由「保存」写入文件。清空单元格是撤销修改，而不是写入空字符串；只保存改动过的内容，以免编辑一个单元格时抹掉其余内容。

词典与程序的核对

词典界面不仅回答「这里写了什么」，还回答「它与程序是否一致」。表格上方有四个数字，每次打开时都会计算，而不是按按钮才算：

数字含义
程序中的键数代码本身声明了多少行——用于核对的基准
词典中的行数人的文件里有多少行，包括未翻译的占位条目
未翻译程序里的键没有可显示的内容：用户编辑和随包提供的部分都没有文本——它们会以英文输出
无键文件中左半部分在程序里已不存在的行：键被重命名或删除，译文却留了下来

这些数字各自独立计算，前两个相等并不能说明什么：键可能恰好一一错开。因此旁边放的是发现项，每一项都可点击——「未翻译」和「无键」会筛选表格。无键的行不能简单丢弃：保存时它不会丢失，否则第一次编辑就会抹掉程序目前还无从挂靠的译文。

由此得到的第二点：「创建」按钮不再写空占位文件。它会生成包含程序全部键、右半部分为空的文件——占位内容一眼就能看到全貌，「未翻译」的数量也如实等于键的数量。文件本身仍然有效：右半部分为空是占位，不是损坏。

发给模型的内容，以免术语不一致

请求不是字符串列表，而是一个带两个键的对象：strings（要翻译什么）和 glossary（同一词典中已经确定的配对）。术语表由该条目集中已翻译的字符串汇总而成——短标签排在前面——并在处理过程中不断补充，因此同一个概念不会在相邻批次里得到不同的词。指令明确要求：glossary 中的词不重写，一个概念在整个回答中只用一个准确术语，不得使用有歧义的词、逐字直译和已确定术语的同义词；而且这些是标签，不是句子。

批次为什么是这个大小

工作模型的推理和回答共用同一份输出 token。在现用模型上的实测（法语，面板条目集）显示出完整性在哪里结束：

法语：完整走通全流程，不转换数据库

已在现用数据目录上验证：语言 fr 在注册表中声明，创建了空的 i18n/fr.txt 和 i18n/panel.fr.txt，用与按钮相同的代码由工作模型填充，并在启动时向宿主声明——该语言同时出现在记忆宫殿和界面这两个切换器中。此过程没有触发向量重算：引入语言无需改动数据库。

那次运行的结果：消息词典中 481 行里有 468 行，面板词典中 493 行里有 478 行。剩余部分是逐一分析过的，而不是归咎于「模型做不到」。消息条目集里有十三行只由占位符构成的占位项（「{reason} {count}」「, 」「—」）：里面没有可翻译的内容，如今它们根本不会进入请求。其余十二个是在法语中与英语写法相同的词（Provenance、messages、base、Pause、Concepts、contradiction、Adjacent、consolidation、Jev）：译文会与原文相同，而按规则相同即表示「没有译文」——这是对的，法语用户看到的就是同一个词。

截至 23.10 的状态（现用数据目录）：fr.txt 中有 460 对，右半部分没有一个为空，panel.fr.txt 中有 480 对。此后键集增长到 488，因此法语词典里又出现了「未翻译」的行——这是正常状态，不是故障：新键以英文进入，直到有人用同一个按钮把它们翻译出来。词典与程序的核对正是为这种情况而出现的（见上文）。

术语并非直译：Room → Salle，Corridor → Couloir，Placard → Cartel（博物馆标牌，而非“placard”——柜子），Memory Palace → Palais de mémoire，Tour → Visite。

运行之后有两处修改。第一：某个批次一对都没被接受（模型把整个上限都消耗在推理上）时，将其一分为二重新询问——否则填充会以「模型达到上限」错误中止——用户看到的便是半成品词典。第二：指令中补入了工具本身的含义（宫殿是记忆存储，房间是类别，走廊是关联，牌匾是记忆的标题，重复是间隔），因为像 Pause 或 Capture 这样的短标签，模型会以有歧义为由拒绝翻译。

为什么俄语不在代码里 俄语是我们第一次「以数据承载语言」的实践，并且完整走通了：485 条文本放在一个文件里，修改无需重新构建，随包层与用户层，与键集合的一致性检查。第二次是法语：空词典，由模型翻译，两个切换器里都有该语言，没有为语言改动任何一行代码。这已不是假设，而是验证过的路径。

6.模型、绑定与向量维度

模型不是在“设置里”选择，而是按宫殿的语言选择。规则只有一条：bindings.json 中的绑定 语言 → 模型，否则使用默认 *。单独的设置可以覆盖该选择，但这是有意的例外，不是常规路径。

// registry/models.json — что модель умеет
{ "id": "Xenova/paraphrase-multilingual-MiniLM-L12-v2",
  "label": "minilm-l12",          // короткое имя: попадает в метку базы
  "pooling": "mean", "dtype": "q8", "dimensions": 384 }

// registry/bindings.json — какой моделью считать язык
{ "bindings": { "zh": "Xenova/bge-small-zh-v1.5", "*": "Xenova/paraphrase-multilingual-MiniLM-L12-v2" },
  "default": "en" }

这里要注意什么

  • 维度来自模型目录，而非代码。bge-small-zh 是 512 个数，多语言的 minilm-l12 是 384。重算从那里取预期长度；转换器里不再有常量。
  • 模型的语言不是标志。中文模型并不意味着“中文库”：语言取自标记，模型取自绑定。同一个多语言模型可以服务俄语、英语和法语，而各库的标记会不同。
  • 维度对写入是硬条件，对读取是软条件。不能写入长度不符的向量：它无法与其他向量比较。可以读取长度不符的库——搜索会退化为按词搜索，但不会沉默，也不会丢失记忆。
  • 包的默认值（default）只有在发行版确实为其携带文本时才被接受。声明了但内容为空的语种比英语更糟。
  • 远程模型是单独的选择。如果设置里选了 OpenAI 兼容端点，本地行根本不会被选中，而维度由第一个向量得知：这类模型没有地方声明维度。库的标记仍按同样方式拼装——由语言和名称——否则库就没有可核对的对象。

7.库的模式：处理器如何判断什么存放在哪里

带向量的表清单不应存在于代码中。否则作者新增的表会悄无声息地从我们所有操作中掉出：重算、修复、状态检查。因此它被声明为数据——文件 registry/schema.json——并按与模型目录相同的规则读取：随包提供是必须的，数据目录中的用户层会覆盖它。

声明什么，推导什么

  • 声明：表的 role（user 或 service）、供模型使用的文本字段（properties.vector.text）以及行的参与条件（properties.vector.where）。
  • 推导：向量字段就是表行中唯一的 BLOB 类型字段。如果有两个 BLOB 字段，声明会被拒绝并给出异议：不清楚该往哪里写。
  • 完全不声明：维度。维度由标签从模型目录推出，而不是来自模式文件。
{ "formatVersion": 1, "schemaVersion": 13,
  "tables": {
    "nodes":        { "role": "user",
                      "properties": { "vector": { "text": "content", "where": "status = 'active'" } },
                      "fields": { "id": "TEXT", "content": "TEXT", "embedding": "BLOB", "...": "..." } },
    "observations": { "role": "user",
                      "properties": { "vector": { "text": "belief", "where": null } } },
    "nodes_fts":    { "role": "service" }
  } }

列出服务表是为了直观说明：遍历器会跳过带标记的对象而不分析内容——FTS 影子表不携带用户向量，试图处理它们会是错误。对 observations 来说，条件 null 表示「所有行都参与」：观察项的归档方式与记忆不同。

七种状态与四种动作

状态看到什么动作
absent数据库文件尚不存在（由作者代码创建）none
empty文件存在，模式作用域内没有记录none
no-label没有标记；模型按向量长度推断write-label 或 convert
other-model有标记，但模型不是我们要写入的那个convert
mixed-dims向量长度与标记不符convert
missing-vectors部分记忆没有向量repair
normal标记一致，所有向量都是该长度none

检查的顺序很重要且是固定的：在弄清这是谁的库之前，不能先报出不匹配——否则别人的模型看上去就像损坏的向量。规则是纯的：它接收关于数据库的事实与期望值，返回状态和动作。因此它可以用不带磁盘、不带 SQLite 的测试来验证，面板只是把它用文字说出来。

重算如何进行

  1. 计划阶段。一个单独的只读连接遍历声明中的表，选出该作用域内向量为空或长度不等于期望值的行。
  2. 分批。文本按每批 16 条送入模型：模型的输出上限不应决定整个数据库的命运。
  3. 写入。向量由存储层写入——数据库只有一个连接，它就活在那里。转换器只负责读取和计算。
  4. 标记。重算成功后，数据库标记被改写为新的语言与模型。标记和向量在一次操作中变更，而不是两次。

空文本不是故障，而是关于内容的事实：这一行没有可用来构建向量的东西。这类行会以单独的数字报出，既不会被静默跳过，也不会被混进总的错误计数。

修复：补算向量并重新标记，而不改变语言

状态 missing-vectors 指那些向量为空、而标记本身可能是正确的记忆。为了六行去跑整个数据库的重算既不必要也有害：其余的向量已经是对的。所以这个状态有自己的动作——repair，按钮会连续发出两个请求来执行它：base-label 补上缺失的标记，base-convert 补算缺少向量的部分。

实际意义：带无向量记忆的数据库在点一次之后就不再被称为「需要修复」，而为此既不必改记忆宫殿的语言，也不必改模型。这样修复的代价恰好是对缺失部分做一次重算，而不是整个文件。

边界：我们有意不构建的东西

  • 没有恢复机制。转换是人的一次性动作；不提供回退到先前状态。只需要一个检查点，让被中断的重算可以续跑：部分重算过的数据库处于 mixed-dims 状态，再次运行会把它跑完。
  • 重算直接在现用库上进行，没有临时副本：库不大，而副本会让空间和时间翻倍。备用途径是导出数据库，作者本来就有这个功能。
  • 无法转换的内容单独列出。重算失败的行不会丢失，也不会阻塞其他行：它会带着原因进入报告的单独列表。
重算不做什么 不改变记忆文本，不创建也不删除表，不碰服务表。计划阶段是只读的：如果没走到点击「执行」那一步，数据库里仍是同样的行、文本、向量和标记。这是测出来的，不是承诺的。

8.人工维护的档案：规则为何单独成为一个包

记忆宫殿里有两类关于人的知识：推导出的档案（系统自己推导出来的东西）和人工维护的区块——人通过 engram_profile_edit 自己写下的规则。后者比前者更优先，而陷阱正在这里。

问题出在哪

人工维护的区块被插到会话开头，与推导出的档案和历史记忆混在一起，处在同一段记忆文本里。智能体在旁边读到「人维护的规则」和「可能不正确的记忆」，除了措辞之外没有任何办法区分它们。问题的另一半是记忆区块本身：里面会混进人并没有写过的内容，而它们看起来和规则一样。

做了什么

规则以单独的包 <engram_profile> 下发，并带有自己的指示性文件头：这是人的指令，必须执行并视为最高优先——与下面只是素材的记忆不同。之所以需要单独的标签，是为了让防替换检查能够把带标记的包与只是看起来像标记的文本区分开。

两次尝试，第一次被取消 起初想做一个「廉价改动」：在已有的记忆块内部补一段头部。后来取消它，改做更贵但正确的事：头部放在共用文本里，并不能把规则和记忆分开，只会再加一种可能与内容混淆的表述。单独的包——单独的位置、单独的标签、单独的校验。

这带来了什么

  • 人的规则能单独看见，不与系统的结论混在一起——对人、对智能体、对安全检查都是如此。
  • 块不会被「稀释」：不是人写的东西不会混进去。
  • 编辑、回滚和版本历史都在同一处，并带乐观锁：一次编辑不会无声地覆盖别人的编辑。

9.过程中我们修了什么，为什么

工作不是绕开作者的代码进行的，而是穿过它进行的：做多语言的过程中，一些妨碍推进的缺陷浮了出来。下面是顺手修掉的部分。这不是「顺便重写」：每一条都曾经造成过阻碍，不处理它，下一步就走不下去。

界面

  • 面板菜单不再跟着滚走。菜单和标签页原本是滚动内容的一部分，于是页面会从它们下面「滑过去」，列表一长菜单就看不见了。现在菜单固定在顶部，不参与内容滚动。同一原因下也重做了层：词典编辑的全屏界面原本「在点击处」打开，卡片一长就落到下边缘之外——从外面看就像「点了没反应」。现在层位于可滚动区域之外。
  • 词典界面的按钮活了过来。保存、取消和用模型填充原先只是没有处理器的标记：界面能打开，之后就什么也不发生。现在只保存改动过的内容，空格子会撤销编辑，而填充写入的是草稿，不是文件。
  • 面板语言跟随宿主。原先面板保留自己的选择，可能在宿主已切到另一种语言时仍说着上一种。现在来源是 DSH 的设置，而手动选择面板语言仍是有意的覆盖。
  • 维护卡片的文案来自面板内置的词典。卡片原先读的是服务端语言文件，因此它的标签不会随界面一起切换，可能停在人没料到的语言上。
  • 完整的模型标识已从选择行里移除（Xenova/paraphrase-multilingual-MiniLM-L12-v2 取代了短名，占满整行并把其余内容挤走）。标识保留在悬停提示中。
  • 面板的校验窗口：按钮靠右，关闭会告知面板（否则窗口只能打开一次——面板以为它还开着），文字更大、对比更强：这个窗口里灰色的 11–12 px 根本读不清。

记忆与宿主

  • 会话日志不在启动时读取。完整读取一份日志在每次启动时要花几百兆内存；在真实数据上宿主因此崩溃。对话回合取自当前会话，日志只在明确请求历史填充时才读。磁盘上的日志本身没有人删除：它们留着，删除是另一个带确认的动作。
  • 对话语言只认人亲手输入的内容。实测表明：「对话语言」被判成英语，因为英文的服务性文本（运行时快照、技能目录、指令）被当成了人的话语。现在凡是没有人类回合标记的内容，一概不计入。
  • 嵌入器会正确关闭，否则重载模型之后资源会一直挂着。

数据与向量

  • 维度在写入时是硬条件，在读取时降级。原先维度不匹配只是一条警告：库里会被悄悄塞满与任何东西都比不上的向量。现在写入会被明确拒绝，而读取继续以按词检索的方式工作——并用 degraded 标记说明这一点，而不是一言不发。
  • 库的维度取多数向量的维度，而不是随手取第一个：混杂不再冒充「常态」。
  • 声明格式版本不再是死字段：formatVersion 会被核对，其他版本的声明不会被默默应用。
  • 迁移记录用文字呈现，而不是一段 JSON：人读的是结论，不是结构。
  • 记忆宫殿日志的清理按钮，带确认和清楚的结果说明。
为什么文档里要有这份清单 因为这些改动有一半改变的是作者视为自己的行为。它们不能只是「知悉」，要么进上游，要么被有意识地拒绝。每个改动都是一个单独的提交，说明写在正文里，便于逐条拆开看。

11.维护：库状态、修复与日志

维护卡片连续回答三个问题：库现在怎么样、按下按钮后它们会怎样、以及上一次为什么结果就是这样。第三个问题以前没有答案——而且这一点很明显。

三个词代替七种状态

规则把库归入七种状态之一（第 7 章），但卡片前的人不需要七种：他只有一个按钮。所以卡片把状态归纳成三个词，而词是按按钮将要做什么来选的：

卡片中的词何时「执行」会做什么
库正常所有库处于 normal、absent 或 empty 状态什么也不做：没有可点的
库需要修复只需要标记和补算向量修复：base-label，然后 base-convert
库需要转换至少有一个库需要重算到另一个模型用组装好的条件切换语言，或者按状态重算

在卡片内部，每个库仍然标明它自己的状态——无标记、另一个模型、向量错序、无向量的记忆——否则就分不清六个库中该修哪个。汇总的词对所有库只有一个：按钮只有一个，它必须诚实地说明自己。

日志：此前没有的两条记录

Jev 的失败决策此前只活在进程内存的环形缓冲区里。缓冲区随重启一起消失，过了一天，日志里「记忆按干净规则通过」和「Jev 保持沉默」就再无法区分。现在每次失败都会写一行 jev-fallback：在哪里询问的（band 或 contradiction）、什么问题、什么原因、花了多久。记忆正文不会进入日志：日志不该成为他人记忆的第二份存储，而日志自身的错误也无权破坏记忆写入——所以它在那里被静默吞掉。

第二行是 vectors-missing。当记忆合并（distill）已经完成、却没有东西可用来写入向量时，它就会出现：库里留下了没有向量的记忆。其中包含记忆数量和作用域。这正是之后显示为「库需要修复」的那种情况；以前原因会消失，人只看到后果。

面板用俄语读这两行，而不是用服务名：操作列表里显示的是「Jev 决策失败」和「没有向量的记忆」，并在提示里给出解释。

Jev 检查行

「检查连接」按钮曾用浮层提示显示结果，而浮层提示只活几秒：过一分钟就既说不清检查发往哪里，也说不清它如何结束。现在表单上方有一行参数——地址、模型、超时，以及密钥的来源（「来自字段」「已保存」「未设置」）——下方是最近一次检查的结论：时间、响应耗时、ping 概率和 HTTP 状态码。

失败有了名字。以前任何失败看起来都一样——「未说明」，人不知道要修密钥、网络、超时还是协议。现在失败的类别会说出来：HTTP（服务器回了，但回的不是那个）、网络（没打通）、超时（没来得及）、协议（响应到了，但没法解析）。错误全文放在提示里，免得这一行被撑开。

测量取自现用连接：这一行显示响应本身返回的耗时和概率，而不是最近一次已知的成功值，旁边还有 HTTP 状态码。其中的数字每次运行都会变——这正是它还活着的标志。
